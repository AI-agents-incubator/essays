# Claude Code vs Codex

Сравнение основано только на двух файлах этого репозитория:
- `claudecode_process_1.md`
- `codex_process_1.md`

Задача этого документа не в том, чтобы объявить одного агента "лучше" другого, а в том, чтобы привести их к общей системе координат:
- какие функции у них совпадают;
- как каждая функция реализуется;
- для каких типов задач один агент выглядит сильнее другого;
- где различие связано не столько с продуктом, сколько с тем, как устроен сам исходный документ.

## Короткий вывод

Если нужен **детально разложенный прикладной pipeline от Figma до production**, в этих материалах сильнее раскрыт **Claude Code**.  
Если нужен **формализованный control plane для автономности, политик, конфигов, встроенных subagents, skills и recurring automation**, в этих материалах сильнее раскрыт **Codex**.

Иначе говоря:
- **Claude Code** в этих файлах описан как практический оркестратор проектной работы.
- **Codex** в этих файлах описан как более формализованная агентная платформа с явными runtime-настройками и официальными механизмами управления.

## Главная асимметрия источников

Перед сравнением важно зафиксировать один момент.

`claudecode_process_1.md` в первую очередь показывает **методологию и pipeline**:
- как организовать routing;
- как разложить работу на skills и субагентов;
- как строить путь `Figma -> ТЗ -> frontend + database -> SQLite -> Supabase -> deploy -> Playwright`.

`codex_process_1.md` в первую очередь показывает **официальные механизмы продукта**:
- `AGENTS.md`;
- `config.toml`;
- `approval_policy`;
- `sandbox_mode`;
- `rules`;
- `web_search`;
- `automations`;
- built-in и custom subagents;
- skills как native-механику;
- MCP как системный слой подключения инструментов.

Поэтому сравнение ниже отвечает на вопрос: **что видно из этих двух документов как из рабочих моделей двух систем**, а не на вопрос "какой продукт абсолютно мощнее вообще во всём".

## Совпадающие ядра возможностей

Несмотря на разницу в подаче, в двух документах хорошо видно общее ядро.

Оба агента поддерживают одну и ту же базовую идею:
- есть слой инструкций;
- есть слой инструментов;
- есть слой делегирования;
- есть повторяемые методологии;
- есть внешние интеграции;
- есть возможность довести работу до частичной или глубокой автономности.

Если убрать названия файлов и синтаксис, обе системы можно описать одинаковой формулой:

`инструкции -> маршрутизация -> агентные роли -> навыки -> инструменты -> проверки -> автономный запуск`

Это означает, что выбор между ними обычно определяется не вопросом "умеет ли агент вообще делать X", а вопросом:
- насколько нативно это встроено;
- насколько формально управляются риски;
- насколько удобно строить длинные пайплайны;
- нужен ли больше контроль platform/runtime или больше прикладная проектная оркестрация.

## Где Claude Code выглядит сильнее

По содержанию `claudecode_process_1.md` Claude Code особенно силён в следующих сценариях:

### 1. Figma -> спецификация -> реализация

Документ очень подробно описывает:
- подключение Figma MCP;
- анализ экранов;
- извлечение design context;
- генерацию ТЗ;
- самопроверку ТЗ против макетов;
- превращение ТЗ в основу для автономной реализации.

Это делает Claude Code особенно подходящим для кейсов, где исходной точкой является дизайн, а выходом должен стать рабочий проект.

### 2. Оркестрация сложного software pipeline

Файл раскладывает реальную работу на цепочку фаз:
- анализ;
- спецификация;
- параллельная сборка frontend и database;
- consistency checks;
- локальная интеграция;
- миграция в Supabase;
- deploy;
- E2E и visual testing.

То есть Claude Code в этих материалах раскрыт как агент для **сборки и доведения продукта до результата**, а не только как инструмент для отдельных задач.

### 3. Методологическая декомпозиция

Очень сильная сторона документа — ясное разведение:
- оркестратора;
- субагентов;
- skills;
- tools;
- data contract;
- тестов как сравнения двух артефактов.

Это полезно для команд, которым нужен не просто агент, а воспроизводимый способ организовать разработку.

## Где Codex выглядит сильнее

По содержанию `codex_process_1.md` Codex особенно силён в следующих сценариях:

### 1. Управляемая автономность

В документе намного глубже раскрыты:
- `sandbox_mode`;
- `approval_policy`;
- `rules`;
- `web_search`;
- internet access;
- профили конфигурации;
- границы "что разрешено вообще" и "что разрешено без отдельного approval".

Это критично для production- и ops-кейсов, где важно не только "что умеет агент", но и "что он имеет право сделать".

### 2. Нативные skills и subagents

В файле Codex skills и subagents выглядят не как инженерная договорённость проекта, а как собственные сущности платформы:
- built-in subagents;
- custom agents в TOML;
- progressive disclosure у skills;
- limit'ы на глубину и количество агентных потоков.

Для повторяемой работы в нескольких проектах это делает систему более предсказуемой и более стандартизируемой.

### 3. Background automation и recurring work

Отдельный слой `automations`, recurring задачи и worktrees делают Codex особенно удобным для кейсов вроде:
- регулярных проверок;
- фонового мониторинга;
- scheduled research;
- recurring repo maintenance;
- периодических обзорных отчётов.

То есть Codex в этих материалах сильнее как платформа для **операционного агентного режима**, а не только для разовой сессии.

## Практическое правило выбора

Если опираться именно на эти два файла, то правило выбора можно сформулировать так:

### Выбирай Claude Code, если

- у тебя дизайн и продуктовая логика являются первичным входом;
- нужно превратить макеты и user flow в ТЗ;
- нужно разложить реализацию на несколько фаз и ролей;
- нужен агент как проектный оркестратор сборки приложения;
- важна методология `spec -> build -> test -> deploy`.

### Выбирай Codex, если

- важнее governance, approvals и sandbox;
- нужен агент как управляемая runtime-платформа;
- нужны native skills, built-in subagents и custom agent profiles;
- важны recurring automations, worktrees и фоновые задачи;
- хочется стандартизировать агентную работу на уровне конфигов и правил, а не только на уровне проектного playbook.

### Выбирай смешанную стратегию мышления, если

- ты хочешь взять у Claude Code **прикладной pipeline**;
- а у Codex взять **формальную модель управления автономностью и конфигами**.

Именно такая комбинация выглядит наиболее сильной:
- от Claude Code взять способ декомпозиции продуктовой работы;
- от Codex взять строгость runtime-контроля, safety и reusable platform setup.

## Самое важное различие одним предложением

В этих материалах **Claude Code** выглядит как лучший кандидат на роль **проектного автономного исполнителя полного software pipeline**, а **Codex** выглядит как лучший кандидат на роль **формально управляемой агентной платформы с более явным control plane**.

## Итог

Оба агента пересекаются почти по всем базовым функциям:
- инструкции;
- skills;
- субагенты;
- tools;
- MCP;
- браузерные сценарии;
- автономная работа.

Но точка силы у них в этих документах разная:
- **Claude Code** сильнее в прикладной проектной сборке и маршрутизации полного цикла.
- **Codex** сильнее в нативной формализации механизмов, безопасной автономности и операционном управлении агентом.

Если задача звучит как **"собери мне проект из макетов и доведи до production"**, по этим материалам первым кандидатом выглядит Claude Code.  
Если задача звучит как **"настрой мне надёжную агентную среду с профилями, политиками, recurring automation и контролем риска"**, по этим материалам первым кандидатом выглядит Codex.
