Ну, как раз моя цель в отношении проверки собственных ресурсов — именно выявление уязвимостей. То есть где дыра. Очевидно, что если эти уязвимости показывают, как можно получить доступ к уровню админ, то с этим уже можно сделать все что угодно. Загрузить любой эксплойт и так далее. Это уже, это уже неинтересно. Но ты понимаешь, да, то есть если дыра найдена, с ней нужно сделать все что угодно, это является важным. Наличие дыр с пониманием, как их закрыть. А вот остальное я с тобой согласен, как бы нет задачи там чего-то загружать, какую-то там полезную нагрузку, что-то делать и так далее. # ТЗ: Red Team Toolkit (концептуальный документ)

**Версия 0.2 · Статус: утверждённый концепт · Реализация не начата — старт только по отдельной команде владельца**

*История: v0.2 — добавлены §8.1 (матрица «движок vs кастом»), пакет правок ROE (§5.1/§5.3/§5.6, §8, приёмка M1), §5A (сетевой контейнмент внешних движков).*

## 1. Преамбула и мотивация

Владелец имеет несколько публичных сервисов и сайтов. Пассивного анализа «уязвимостей в дикой природе» недостаточно: реальный атакующий не сканирует — он **проникает, закрепляется и наносит ущерб** (прецедент: несколько лет назад сайт владельца был уничтожен внешним атакующим). Цель инструмента — **воспроизвести реальный kill chain против собственных активов**, найти пути компрометации раньше атакующего и устранить их.

Ключевой принцип: инструмент доказывает воздействие (**proof-of-impact**), а не сообщает «потенциальную уязвимость». При этом доказательство всегда **неразрушающее** (см. §5 ROE).

## 2. Цели и задачи

| # | Цель | Критерий достижения |
|---|------|---------------------|
| G1 | Эмуляция полного kill chain: recon → exploit → access → impact | Сквозные цепочки атак воспроизводятся автоматически |
| G2 | Proof-of-impact вместо теоретических находок | Каждый critical/high finding содержит evidence успешной эксплуатации |
| G3 | Повторяемость и регресс | Прогоны по расписанию, diff отчётов «стало хуже/лучше» |
| G4 | Приоритизация устранения | Отчёт с severity, шагами воспроизведения и remediation |
| G5 | Безопасность самого процесса | Инструмент физически не может выйти за scope и нанести необратимый ущерб |

## 3. Модель угроз

- **ATK-1 (black box)**: внешний анонимный атакующий без кредов. Цели: RCE, доступ к данным, deface, уничтожение сервиса.
- **ATK-2 (grey box)**: атакующий с обычным пользовательским аккаунтом (регистрация открыта) или угневший сессию. Цели: эскалация до admin, доступ к чужим данным (IDOR), кража токенов.
- **ATK-3 (supply/infra)**: атака через инфраструктуру — открытые порты/панели, дефолтные креды, утечки секретов в JS/репозиториях, облачные метаданные (SSRF).

## 4. Область применения

**Только активы владельца** (или с письменным разрешением). Список активов фиксируется в `config.yaml` (allowlist доменов/IP/CIDR). Предпочтительная цель — staging-копии; production — в согласованные окна с пониженной интенсивностью.

## 5. Правила ведения действий (ROE) — жёстко зашиты в инструмент

1. **Scope Guard — два уровня** (внешним бинарникам не доверяем никогда):
   - **A. Application-level (свой код)**: весь собственный HTTP-трафик идёт через httpx-обёртку ядра с тремя проверками: allowlist до запроса; повторная проверка IP после DNS-резолва (защита от DNS rebinding); ревалидация на каждом редиректе.
   - **B. Network-level (внешние движки — отдельные процессы со своим сетевым стеком)**: HTTP-движки (sqlmap, ffuf, nuclei, dalfox) запускаются только с принудительным `--proxy`/`-x` на локальный egress-прокси, пропускающий исключительно allowlist; nmap (сырые пакеты, прокси бесполезен) — только внутри Docker-контейнера с egress-правилами (iptables / изолированный docker network), разрешающими лишь IP из allowlist. Прямой egress запрещён, fail-closed: контейнмент не поднялся → движок не стартует.
   - **Инфраструктурный allowlist**: OOB-сервер interactsh — осознанный egress вне scope цели, фиксируется явно отдельным списком.
   - **Containment self-test (гейт старта)**: перед каждым прогоном orchestrator шлёт canary-запрос к заведомо вне-скоповому хосту на уровнях A и B и требует блокировки. Тест не пройден → прогон не стартует.
   - Детальный дизайн уровня B (enforcing-прокси, nftables, контролируемый DNS-резолвер, тесты T1–T6) — см. **§5A**.
2. **Неразрушающая эксплуатация**: доказательство impact только через безопасные артефакты — canary-файл/токен, OOB-callback, вывод `id`/`hostname`, чтение **тестовых** записей (с limit). **Запрещено навсегда**: `DROP/DELETE` реальных данных, deface, шифрование, exfil персональных данных, DoS (кроме controlled rate-limit проверок).
3. **Авто-откат (журнал операций)**: каждый модуль в момент создания/изменения состояния регистрирует rollback-действие (ID созданной сущности, путь загруженного файла, команда удаления). При завершении прогона или kill-switch orchestrator выполняет стек отката в порядке LIFO и верифицирует удаление. Отчёт фиксирует cleanup-статус по каждому артефакту; неудалимое автоматически → явная пометка `manual cleanup required`.
4. **Kill-switch**: файл `STOP` в рабочей директории или SIGINT → немедленная остановка всех воркеров + отчёт о прогрессе. Порядок остановки при работающих внешних движках (сначала обрубить сеть, потом cleanup) — см. §5A.8.
5. **Audit log**: каждый запрос (метод, URL, payload-хэш, код ответа) пишется в журнал прогона.
6. **Evidence-хранилище и маскирование**: отчёты содержат маскированные значения (`sk-...****`) + ссылку на evidence-ID. Полные значения — в локальном шифрованном хранилище (age/Fernet), ключ вне репозитория (env / macOS Keychain). Retention: автоудаление evidence через 30 дней.

## 5A. Контейнмент внешних движков (дополнение к §5 ROE)

**Статус: утверждённое архитектурное решение (v0.2). Детализирует уровень B из §5.1 и периметр из §8. Реализация — по отдельной команде владельца.**

### 5A.1. Проблема, которую закрывает уровень B

Application-level guard (уровень A §5.1) полностью контролирует собственный код toolkit на httpx — **и только его**.

Внешние движки из §8 (`sqlmap`, `nmap`, `ffuf`, `nuclei`, `interactsh`-клиент, `dalfox`, `gitleaks`, …) — это **отдельные процессы с собственным сетевым стеком**. Они не проходят через наш httpx-клиент, а значит application-level guard их не контролирует вообще. Конкретные пути ухода за scope:

- `sqlmap` следует за редиректом или submit'ит форму на сторонний хост;
- `nuclei` прогоняет тысячи шаблонов, часть из которых обращается к внешним ресурсам;
- `ffuf` при неверном словаре/таргете создаёт нагрузку уровня DoS на rate-limiter;
- `nmap` вообще не говорит по HTTP — сырые пакеты, никакой прокси его не удержит;
- любой движок при DNS-round-robin/CDN может уехать на IP вне ожидаемого.

Вывод: **Scope Guard в этом проекте — не одна сущность, а два независимых периметра.** Application-level для своего кода (§5.1-A) и network-level контейнмент для чужих бинарников (описан ниже). Docker-образ из §8 при этом — не «удобство запуска», а обязательный периметр безопасности.

### 5A.2. Модель двух периметров

```
┌─────────────────────────────────────────────────────────────┐
│  Docker container (--cap-add=NET_ADMIN, default-deny egress) │
│                                                              │
│   ┌───────────────┐        ┌──────────────────────────────┐ │
│   │ Своё ядро     │        │ Внешние движки               │ │
│   │ (httpx)       │        │ sqlmap / nmap / ffuf / nuclei │ │
│   │  §5.1 guard   │        └──────────────┬───────────────┘ │
│   └──────┬────────┘                       │                 │
│          │                    HTTP(S)     │  raw packets     │
│          │              ┌─────────────────▼──────┐          │
│          │              │ Периметр A:            │          │
│          │              │ enforcing-proxy        │          │
│          │              │ (allowlist по host)    │          │
│          │              └─────────────┬──────────┘          │
│          └────────────────────────────┤                     │
│                                        ▼                     │
│              ┌──────────────────────────────────────────┐   │
│              │ Периметр B: egress-firewall (nftables)   │   │
│              │ allow = resolved allowlist IP/CIDR + OOB  │   │
│              │ default = DROP + log                      │   │
│              └───────────────────┬──────────────────────┘   │
└──────────────────────────────────┼──────────────────────────┘
                                    ▼
                              внешняя сеть
```

Периметр A ловит уровень приложения (host-based scope + аудит). Периметр B — последняя линия: даже если движок обошёл прокси или это `nmap`, пакет на IP вне allowlist физически не выйдет из namespace. **Оба fail-closed**: сбой построения любого периметра = нет egress, а не «открыто по умолчанию».

### 5A.3. Периметр A — enforcing-прокси для HTTP-движков

Локальный async-прокси (mitmproxy или собственный на том же asyncio-стеке), через который **принудительно** гонятся все HTTP-движки:

- `sqlmap --proxy=http://127.0.0.1:8080`
- `nuclei -proxy http://127.0.0.1:8080`
- `ffuf -x http://127.0.0.1:8080`
- `dalfox --proxy http://127.0.0.1:8080`

Прямой egress этим процессам запрещён Периметром B, поэтому «мимо прокси» они пойти не могут — только через него или в drop.

Два режима, осознанный размен:

| Режим | Что делает | Плюс | Минус |
|-------|-----------|------|-------|
| **CONNECT-only (по умолчанию)** | Проверяет host из CONNECT/SNI по allowlist, не расшифровывает TLS | Просто, надёжно, не нужен доверенный CA в каждом движке | Аудит только по host, без payload |
| **MITM (опционально)** | Расшифровывает через свой CA, логирует полный запрос | Полный audit + маскирование секретов (§5.6) для внешних движков | Нужно вшить CA в trust store каждого движка |

Для scope-enforcement достаточно CONNECT-only. MITM включается флагом интенсивности, когда нужен глубокий аудит payload'ов.

### 5A.4. Периметр B — egress-firewall / network namespace

Внутри контейнера — `nftables` (или netns с явным ruleset), строящийся **из конфига перед стартом воркеров**:

```
table inet scope {
  chain egress {
    type filter hook output priority 0; policy drop;

    ct state established,related accept
    oifname "lo" accept
    udp dport 53 ip daddr $CONTROLLED_RESOLVER accept   # только контролируемый DNS
    ip daddr @allowlist_v4 accept
    ip6 daddr @allowlist_v6 accept
    ip daddr $OOB_SERVER accept                          # interactsh/OOB callback listener
    log prefix "SCOPE-DROP " counter drop                # §5.5 — дропы в audit log
  }
}
```

- `@allowlist_v4/v6` — наполняется резолвом allowlist-доменов + явными CIDR из `config.yaml`.
- `nmap` контейнментится **только здесь** (прокси ему не помощник) — пакет на IP вне set'а дропается на выходе.
- Любой дроп логируется → уходит в единый audit log (§5.5) с пометкой «попытка выхода за scope».

### 5A.5. DNS и разрешение allowlist — тонкий момент

Network-level фильтрация работает по IP, а allowlist задан доменами → между ними DNS, и тут два подводных камня:

1. **Согласованность.** Firewall и движки должны видеть одни и те же IP. Решение: поднять **контролируемый резолвер** (dnsmasq/unbound в контейнере), который резолвит allowlist-домены и только их; движки ходят в него, из его ответов строится `@allowlist`. Иначе движок резолвит домен в IP-1, firewall знает IP-2 (round-robin/CDN) — и легитимный запрос дропается либо, хуже, левый IP проходит.
2. **TOCTOU / rebinding.** Между резолвом для firewall и реальным запросом IP может смениться. Для «своих активов» это скорее случайный уход, чем атака, но принцип — **fail-closed**: неразрешённый IP дропается, ре-резолв идёт по фиксированному окну, смена IP allowlist-домена логируется как аномалия, а не молча принимается.

CDN-цели (Cloudflare и т.п.) документируются отдельно: allowlist по домену на shared-IP означает, что firewall пропустит весь этот IP — тут scope держится Периметром A (по host), а не B.

### 5A.6. Синергия: прокси как единая точка §5.5 и §5.6

Побочная выгода принуждения всех HTTP-движков через один прокси — он становится **естественной единой точкой** для двух других требований ROE:

- **§5.5 Audit log**: каждый запрос любого движка (метод, URL, хэш payload, код ответа) логируется в одном месте, в едином формате — не нужно парсить разношёрстный stdout каждого инструмента.
- **§5.6 Маскирование секретов**: маскирование (`sk-...****`) применяется централизованно на выходе прокси в отчёт, а не отдельно в каждом модуле.

То есть Периметр A окупается трижды: scope + audit + masking.

### 5A.7. Rate limiting в две ступени

- **Ступень 1 (движок)**: нативные флаги — `nmap --max-rate`, `nuclei -rate-limit`, `sqlmap --delay/--threads`, `ffuf -rate`. Грубый предохранитель.
- **Ступень 2 (прокси)**: общий token-bucket на прокси, видящий **суммарный** HTTP-трафик всех движков сразу. Именно он гарантирует §7-throttling на уровне цели целиком (движки о существовании друг друга не знают и по отдельности легко превысят лимит).

`nmap` (мимо прокси) ограничивается только ступенью 1 + сетевым QoS при необходимости.

### 5A.8. Интеграция с kill-switch (§5.4)

`STOP`-файл / SIGINT должен рвать не только воркеры, но и внешние процессы:

1. SIGTERM → (grace) → SIGKILL всем дочерним движкам по группе процессов.
2. Перевод Периметра B в total-drop (мгновенно обрубает любой inflight-пакет любого движка, даже зависшего).
3. Авто-откат §5.3 (удаление залитых артефактов/тестовых сущностей) выполняется **до** фиксации отчёта о прогрессе.

Порядок важен: сначала обрубаем сеть, потом чистим — чтобы движок в процессе остановки не успел ничего доотправить.

### 5A.9. Cloud metadata — уточнение против ложного правила

Важно не завести ошибочное разрешающее правило. Proof для SSRF (§F3) — это когда **сервер-цель** по нашей инъекции сам обращается к своему `169.254.169.254`; детектируем через OOB-callback. Запрос идёт с инфраструктуры цели, **не** с нашего toolkit.

Следствие: наш собственный процесс к `169.254.169.254` обращаться не должен **никогда**, и Периметр B обязан этот адрес (и `fd00:ec2::254`) **жёстко дропать** — иначе toolkit, запущенный в облаке, рискует слить креды **собственного** хоста. Это правило — «deny», а не «allow».

### 5A.10. Проверка самого контейнмента (тесты pytest)

Контейнмент — самая ответственная часть кода, поэтому он проверяется автотестами наравне с модулями:

- **T1**: каждый движок пытается обратиться к заведомо out-of-scope хосту → ассерт «заблокировано + записан SCOPE-DROP».
- **T2**: `nmap` по IP вне allowlist → пакеты не выходят (проверка счётчика дропов).
- **T3**: `STOP`-файл во время активного прогона → все дочерние процессы мертвы за N секунд, Периметр B в total-drop.
- **T4**: обращение к `169.254.169.254` из процесса toolkit → дроп.
- **T5**: сбой построения ruleset/прокси на старте → контейнер без egress (fail-closed), а не «поехали как есть».
- **T6**: DNS allowlist-домена сменил IP → легитимный трафик не проходит на новый IP без ре-резолва (fail-closed), событие залогировано.

### 5A.11. Матрица «движок → механизм контейнмента»

| Движок | Периметр A (прокси) | Периметр B (firewall) | Rate limit |
|--------|:---:|:---:|---|
| sqlmap | ✅ принудительно | ✅ | delay/threads + прокси-bucket |
| nuclei | ✅ | ✅ | `-rate-limit` + прокси-bucket |
| ffuf | ✅ | ✅ | `-rate` + прокси-bucket |
| dalfox | ✅ | ✅ | прокси-bucket |
| gitleaks/trufflehog | локально (не сеть) | ✅ (если тянет remote) | — |
| **nmap** | ❌ (не HTTP) | ✅ **единственный контроль** | `--max-rate` |
| interactsh-клиент | ✅ к OOB-серверу | ✅ (OOB в allow) | — |
| своё ядро httpx | §5.1-A (уже есть) | ✅ (defense-in-depth) | app-level bucket |

### 5A.12. Влияние на трудоёмкость (честно)

Этот периметр — не «обёртка на день». В оценку M1–M3 добавляются: enforcing-прокси с двумя режимами, генерация nftables-ruleset из pydantic-конфига, контролируемый резолвер, Docker-слой с `NET_ADMIN` и вшитыми бинарниками движков (+ pure-Python fallback при их отсутствии), и тесты T1–T6. Это самая ответственная и самая «скучная» инженерия проекта — и одновременно то единственное, что реально отделяет «инструмент, которому можно доверить aggressive-прогон по production в согласованное окно» от «скрипта, который однажды уедет за scope».

## 6. Функциональные требования (по фазам kill chain)

- **F1 Recon**: субдомены, порты/сервисы, фингерпринт технологий, директории/файлы (ffuf-словари), анализ JS (endpoints, секреты), wayback-машина, открытые панели (phpMyAdmin, adminer, `.git`, `.env`, backup-файлы).
- **F2 Discovery**: SQLi/NoSQLi, XSS (reflected/stored/DOM), SSRF, IDOR, auth-атаки (JWT-манипуляции, weak secrets, session fixation, password policy), security headers/CORS, file upload, XXE, SSTI, open redirect, known CVE по версиям стека, дефолтные креды.
- **F3 Exploitation (proof-of-impact)**: SQLi → извлечение canary-записи; RCE → OOB-callback + безопасная команда; upload → «echo-shell» с авто-удалением; SSRF → чтение cloud metadata (proof); auth bypass → доступ к admin-эндпоинту; blind-кейсы — через OOB (interactsh).
- **F4 Post-exploitation (лайт)**: что доступно с полученной позиции — internal endpoints, права токена, чувствительные файлы конфигурации. **Без** persistence, lateral movement и повреждений.
- **F5 Attack chaining**: граф находок; автоматические цепочки (пример: exposed `.git` → исходники → hardcoded DB creds → доступ к БД → proof). Именно так работает реальный атакующий — это ядро ценности инструмента.
- **F6 Reporting**: JSON + HTML; severity, evidence, шаги воспроизведения, remediation; diff между прогонами; экспорт для трекера задач.
- **F7 Orchestration**: `config.yaml` (target, scope, auth-профили, интенсивность), параллелизм с rate limiting, resume прерванного прогона, профили целей (несколько сервисов владельца).

## 7. Уровни интенсивности

| Уровень | Что разрешено |
|---------|---------------|
| **passive** | OSINT, анализ заголовков/JS/ответов, без единого «атакующего» payload |
| **active** | Payload-инъекции, fuzzing, IDOR-перебор, авторизованные проверки — всё неразрушающее |
| **aggressive** | F3/F4: эксплуатация с proof-of-impact, brute force (rate-limited), chaining. Только staging или согласованное окно |

## 8. Нефункциональные требования

Python 3.12, async (httpx + asyncio), Playwright для браузерных атак, pydantic-валидация конфига, Jinja2-отчёты, pytest для тестов самого инструмента. **Docker — не «удобство запуска», а обязательный периметр контейнмента** для прогонов с внешними движками (§5.1-B, детальный дизайн — §5A): внешние бинарники исполняются только внутри контейнера с egress-ограничениями. Опциональные внешние движки (nmap, ffuf, sqlmap, nuclei, interactsh) — с pure-Python fallback. Модульная plugin-архитектура: новый модуль = один файл + регистрация.

### 8.1 Матрица «движок vs кастом» (архитектурное решение)

**Принцип: пишем меньше, оркестрируем больше.** Battle-tested движки — для commodity-классов уязвимостей; самописный код — только там, где готовых инструментов не существует (glue, guardrails, верификация, chaining, app-specific логика).

| Модуль | Движок (оркестрация) | Самописный слой |
|--------|---------------------|-----------------|
| Порты/сервисы | nmap | нормализация результатов |
| Директории/файлы | ffuf | словари под стек цели |
| Secrets | gitleaks / trufflehog | маскирование в отчёте (ROE §5.6) |
| SQLi | sqlmap (`--batch`, лимиты, scope-обёртка) | выбор точек, верификация evidence |
| XSS | dalfox | Playwright-верификация исполнения в DOM |
| SSRF / blind | interactsh | OOB-корреляция callback ↔ запрос |
| JWT | jwt_tool (+ john для weak secret) | логика auth-flow приложения |
| API fuzzing | schemathesis (по OpenAPI) / nuclei | адаптеры |
| IDOR | — *(движка не существует)* | сравнение ответов двух аккаунтов — кастом |
| Headers/CORS | — | кастом (движок не нужен) |
| Attack chaining (F5) | — | **кастом — ядро ценности** |
| Scope guard / audit / kill-switch / отчёты | — | **кастом — реализация ROE §5** |

**Правила оркестрации:**
1. Каждый внешний движок запускается только через обёртку ядра: scope guard (§5.1), rate limiting, audit log (§5.5). Прямой запуск бинарника модулями запрещён.
2. Движок = детектор; toolkit = верификатор. Finding попадает в отчёт только после независимой верификации evidence (G2).
3. Версии движков пиннятся в Docker-образе; парсинг — через JSON-вывод там, где движок его поддерживает.
4. При отсутствии бинарника — pure-Python fallback (со сниженным покрытием и пометкой в отчёте).

# §5A. Контейнмент внешних движков (дополнение к §5 ROE)

**Статус: черновик архитектурного решения. Дополняет §5.1 и §8. Реализация — по отдельной команде владельца.**

## 5A.1. Проблема, которую §5.1 не покрывает

§5.1 требует Scope Guard «на уровне ядра HTTP-клиента, обойти невозможно без правки кода». Это верно и достаточно — **но только для собственного кода toolkit на httpx**.

Внешние движки из §8 (`sqlmap`, `nmap`, `ffuf`, `nuclei`, `interactsh`-клиент, `dalfox`, `gitleaks`, …) — это **отдельные процессы с собственным сетевым стеком**. Они не проходят через наш httpx-клиент, а значит наш «неубиваемый» application-level guard их не контролирует вообще. Конкретные пути ухода за scope:

- `sqlmap` следует за редиректом или submit'ит форму на сторонний хост;
- `nuclei` прогоняет тысячи шаблонов, часть из которых обращается к внешним ресурсам;
- `ffuf` при неверном словаре/таргете создаёт нагрузку уровня DoS на rate-limiter;
- `nmap` вообще не говорит по HTTP — сырые пакеты, никакой прокси его не удержит;
- любой движок при DNS-round-robin/CDN может уехать на IP вне ожидаемого.

Вывод: **Scope Guard в этом проекте — не одна сущность, а два независимых периметра.** Application-level для своего кода (уже есть в §5.1) и network-level контейнмент для чужих бинарников (описан ниже). Docker-образ из §8 при этом перестаёт быть «удобством запуска» и становится обязательным периметром безопасности.

## 5A.2. Модель двух периметров

```
┌─────────────────────────────────────────────────────────────┐
│  Docker container (--cap-add=NET_ADMIN, default-deny egress) │
│                                                              │
│   ┌───────────────┐        ┌──────────────────────────────┐ │
│   │ Своё ядро     │        │ Внешние движки               │ │
│   │ (httpx)       │        │ sqlmap / nmap / ffuf / nuclei │ │
│   │  §5.1 guard   │        └──────────────┬───────────────┘ │
│   └──────┬────────┘                       │                 │
│          │                    HTTP(S)     │  raw packets     │
│          │              ┌─────────────────▼──────┐          │
│          │              │ Периметр A:            │          │
│          │              │ enforcing-proxy        │          │
│          │              │ (allowlist по host)    │          │
│          │              └─────────────┬──────────┘          │
│          └────────────────────────────┤                     │
│                                        ▼                     │
│              ┌──────────────────────────────────────────┐   │
│              │ Периметр B: egress-firewall (nftables)   │   │
│              │ allow = resolved allowlist IP/CIDR + OOB  │   │
│              │ default = DROP + log                      │   │
│              └───────────────────┬──────────────────────┘   │
└──────────────────────────────────┼──────────────────────────┘
                                    ▼
                              внешняя сеть
```

Периметр A ловит уровень приложения (host-based scope + аудит). Периметр B — последняя линия: даже если движок обошёл прокси или это `nmap`, пакет на IP вне allowlist физически не выйдет из namespace. **Оба fail-closed**: сбой построения любого периметра = нет egress, а не «открыто по умолчанию».

## 5A.3. Периметр A — enforcing-прокси для HTTP-движков

Локальный async-прокси (mitmproxy или собственный на том же asyncio-стеке), через который **принудительно** гонятся все HTTP-движки:

- `sqlmap --proxy=http://127.0.0.1:8080`
- `nuclei -proxy http://127.0.0.1:8080`
- `ffuf -x http://127.0.0.1:8080`
- `dalfox --proxy http://127.0.0.1:8080`

Прямой egress этим процессам запрещён Периметром B, поэтому «мимо прокси» они пойти не могут — только через него или в drop.

Два режима, осознанный размен:

| Режим | Что делает | Плюс | Минус |
|-------|-----------|------|-------|
| **CONNECT-only (по умолчанию)** | Проверяет host из CONNECT/SNI по allowlist, не расшифровывает TLS | Просто, надёжно, не нужен доверенный CA в каждом движке | Аудит только по host, без payload |
| **MITM (опционально)** | Расшифровывает через свой CA, логирует полный запрос | Полный audit + маскирование секретов (§5.6) для внешних движков | Нужно вшить CA в trust store каждого движка |

Для scope-enforcement достаточно CONNECT-only. MITM включается флагом интенсивности, когда нужен глубокий аудит payload'ов.

## 5A.4. Периметр B — egress-firewall / network namespace

Внутри контейнера — `nftables` (или netns с явным ruleset), строящийся **из конфига перед стартом воркеров**:

```
table inet scope {
  chain egress {
    type filter hook output priority 0; policy drop;

    ct state established,related accept
    oifname "lo" accept
    udp dport 53 ip daddr $CONTROLLED_RESOLVER accept   # только контролируемый DNS
    ip daddr @allowlist_v4 accept
    ip6 daddr @allowlist_v6 accept
    ip daddr $OOB_SERVER accept                          # interactsh/OOB callback listener
    log prefix "SCOPE-DROP " counter drop                # §5.5 — дропы в audit log
  }
}
```

- `@allowlist_v4/v6` — наполняется резолвом allowlist-доменов + явными CIDR из `config.yaml`.
- `nmap` контейнментится **только здесь** (прокси ему не помощник) — пакет на IP вне set'а дропается на выходе.
- Любой дроп логируется → уходит в единый audit log (§5.5) с пометкой «попытка выхода за scope».

## 5A.5. DNS и разрешение allowlist — тонкий момент

Network-level фильтрация работает по IP, а allowlist задан доменами → между ними DNS, и тут два подводных камня:

1. **Согласованность.** Firewall и движки должны видеть одни и те же IP. Решение: поднять **контролируемый резолвер** (dnsmasq/unbound в контейнере), который резолвит allowlist-домены и только их; движки ходят в него, из его ответов строится `@allowlist`. Иначе движок резолвит домен в IP-1, firewall знает IP-2 (round-robin/CDN) — и легитимный запрос дропается либо, хуже, левый IP проходит.
2. **TOCTOU / rebinding.** Между резолвом для firewall и реальным запросом IP может смениться. Для «своих активов» это скорее случайный уход, чем атака, но принцип — **fail-closed**: неразрешённый IP дропается, ре-резолв идёт по фиксированному окну, смена IP allowlist-домена логируется как аномалия, а не молча принимается.

CDN-цели (Cloudflare и т.п.) документируются отдельно: allowlist по домену на shared-IP означает, что firewall пропустит весь этот IP — тут scope держится Периметром A (по host), а не B.

## 5A.6. Синергия: прокси как единая точка §5.5 и §5.6

Побочная выгода принуждения всех HTTP-движков через один прокси — он становится **естественной единой точкой** для двух других требований ROE:

- **§5.5 Audit log**: каждый запрос любого движка (метод, URL, хэш payload, код ответа) логируется в одном месте, в едином формате — не нужно парсить разношёрстный stdout каждого инструмента.
- **§5.6 Маскирование секретов**: маскирование (`sk-...****`) применяется централизованно на выходе прокси в отчёт, а не отдельно в каждом модуле.

То есть Периметр A окупается трижды: scope + audit + masking.

## 5A.7. Rate limiting в две ступени

- **Ступень 1 (движок)**: нативные флаги — `nmap --max-rate`, `nuclei -rate-limit`, `sqlmap --delay/--threads`, `ffuf -rate`. Грубый предохранитель.
- **Ступень 2 (прокси)**: общий token-bucket на прокси, видящий **суммарный** HTTP-трафик всех движков сразу. Именно он гарантирует §7-throttling на уровне цели целиком (движки о существовании друг друга не знают и по отдельности легко превысят лимит).

`nmap` (мимо прокси) ограничивается только ступенью 1 + сетевым QoS при необходимости.

## 5A.8. Интеграция с kill-switch (§5.4)

`STOP`-файл / SIGINT должен рвать не только воркеры, но и внешние процессы:

1. SIGTERM → (grace) → SIGKILL всем дочерним движкам по группе процессов.
2. Перевод Периметра B в total-drop (мгновенно обрубает любой inflight-пакет любого движка, даже зависшего).
3. Авто-откат §5.3 (удаление залитых артефактов/тестовых сущностей) выполняется **до** фиксации отчёта о прогрессе.

Порядок важен: сначала обрубаем сеть, потом чистим — чтобы движок в процессе остановки не успел ничего доотправить.

## 5A.9. Cloud metadata — уточнение против ложного правила

Важно не завести ошибочное разрешающее правило. Proof для SSRF (§F3) — это когда **сервер-цель** по нашей инъекции сам обращается к своему `169.254.169.254`; детектируем через OOB-callback. Запрос идёт с инфраструктуры цели, **не** с нашего toolkit.

Следствие: наш собственный процесс к `169.254.169.254` обращаться не должен **никогда**, и Периметр B обязан этот адрес (и `fd00:ec2::254`) **жёстко дропать** — иначе toolkit, запущенный в облаке, рискует слить креды **собственного** хоста. Это правило — «deny», а не «allow».

## 5A.10. Проверка самого контейнмента (тесты §pytest)

Контейнмент — самая ответственная часть кода, поэтому он проверяется автотестами наравне с модулями:

- **T1**: каждый движок пытается обратиться к заведомо out-of-scope хосту → ассерт «заблокировано + записан SCOPE-DROP».
- **T2**: `nmap` по IP вне allowlist → пакеты не выходят (проверка счётчика дропов).
- **T3**: `STOP`-файл во время активного прогона → все дочерние процессы мертвы за N секунд, Периметр B в total-drop.
- **T4**: обращение к `169.254.169.254` из процесса toolkit → дроп.
- **T5**: сбой построения ruleset/прокси на старте → контейнер без egress (fail-closed), а не «поехали как есть».
- **T6**: DNS allowlist-домена сменил IP → легитимный трафик не проходит на новый IP без ре-резолва (fail-closed), событие залогировано.

## 5A.11. Матрица «движок → механизм контейнмента»

| Движок | Периметр A (прокси) | Периметр B (firewall) | Rate limit |
|--------|:---:|:---:|---|
| sqlmap | ✅ принудительно | ✅ | delay/threads + прокси-bucket |
| nuclei | ✅ | ✅ | `-rate-limit` + прокси-bucket |
| ffuf | ✅ | ✅ | `-rate` + прокси-bucket |
| dalfox | ✅ | ✅ | прокси-bucket |
| gitleaks/trufflehog | локально (не сеть) | ✅ (если тянет remote) | — |
| **nmap** | ❌ (не HTTP) | ✅ **единственный контроль** | `--max-rate` |
| interactsh-клиент | ✅ к OOB-серверу | ✅ (OOB в allow) | — |
| своё ядро httpx | §5.1 (уже есть) | ✅ (defense-in-depth) | app-level bucket |

## 5A.12. Влияние на трудоёмкость (честно)

Этот периметр — не «обёртка на день». В оценку M1–M3 добавляются: enforcing-прокси с двумя режимами, генерация nftables-ruleset из pydantic-конфига, контролируемый резолвер, Docker-слой с `NET_ADMIN` и вшитыми бинарниками движков (+ pure-Python fallback при их отсутствии), и тесты T1–T6.
