# State Storage Strategy

> Версия файла: `v1.0`
> Дата версии: `2026-03-16`
> Тип документа: `стратегия хранения состояний`

## Зачем нужен отдельный state layer

Если агентная организация должна жить долго, ей нужно где-то хранить:
- статусы задач;
- очередь работ;
- текущие роли и их назначения;
- идентификаторы прогонов;
- handoff events;
- переменные текущего цикла;
- benchmark history;
- evaluation history;
- learning history;
- ссылки между артефактами и их operational состояниями.

Markdown-файлы хорошо подходят для:
- объяснимости;
- аудита;
- редактирования человеком;
- долгоживущих правил и описаний.

Но для operational состояния они недостаточны.

## Двухслойная модель

Правильная модель здесь такая:

### 1. Artifact layer

Хранит:
- charter;
- policies;
- product/engineering/execution/evaluation/evolution документы;
- явные решения;
- explainability.

### 2. State layer

Хранит:
- актуальные статусы;
- идентификаторы прогонов;
- очереди;
- события;
- связи между сущностями;
- операционные переменные;
- краткоживущие и среднесрочные operational данные.

## Базовая стратегия для v1

### Фаза 1. Локальный `SQLite`

На этапе тестирования и первых benchmark-прогонов state layer должен быть локальным и простым.

Поэтому default-стратегия для v1 такая:

- один локальный `SQLite` store внутри runtime sandbox;
- schema хранится в репозитории;
- данные создаются и читаются только в пределах своей песочницы;
- база служит operational memory, а не источником policy;
- markdown-артефакты остаются читаемым control plane.

Почему это правильно:
- просто поднять;
- легко тестировать;
- легко сбрасывать и воспроизводить;
- удобно для sandbox-режима;
- достаточно для первых независимых прогонов.

### Фаза 2. `Supabase / Postgres`

Когда базовая архитектура подтвердит свою работоспособность, state layer должен перейти на более устойчивую сетевую основу:

- `Supabase` как практичная управляемая реализация;
- либо прямой `Postgres`, если нужно больше контроля.

Это потребуется, когда:
- организация работает неделями и месяцами;
- есть несколько процессов;
- есть параллельные runtime;
- нужна долговременная история;
- нужна многопользовательская или распределённая работа;
- нужна более надёжная observability и querying.

## Что должно оставаться в файлах даже после миграции

Даже при переходе на `Supabase` нельзя переносить всё в базу.

В файлах должны оставаться:
- charter;
- policies;
- templates;
- decision log;
- long-form explanations;
- benchmark definitions;
- expected results;
- comparison findings;
- learning summaries.

То есть база хранит **операционное состояние**, а файловый слой хранит **объяснимую организационную память и правила**.

## Критерий зрелости state layer

State layer считается достаточным, если он позволяет:
- восстановить текущий operational контекст;
- понять состояние очередей и ролей;
- продолжить цикл после паузы;
- не потерять benchmark/evaluation history;
- не смешивать данные двух runtime-песочниц;
- безопасно мигрировать на более надёжное хранилище.
