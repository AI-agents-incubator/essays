# Агент на уровне операционной системы: от терминала к автономной агентной архитектуре

## Ключевая идея

Терминал — это точка входа, а не среда обитания агента. Когда Claude Code запускается через командную строку, он получает доступ не к терминалу, а через терминал — к внутреннему пространству операционной системы. Всё, что происходит дальше, происходит уже на уровне ОС: процессы, файлы, сеть, межпроцессное взаимодействие. Терминал в этот момент — лишь маленькая дверца, через которую агент вошёл. То, что он создаёт внутри, может жить и работать независимо от этой дверцы.

## Важное уточнение: это относится не только к Claude Code

Хотя документ написан на материале `Claude Code`, сам принцип здесь шире.

Если `Codex` работает через терминал, headless-режим или SDK, архитектурная логика та же самая:

- терминал остаётся точкой входа, а не "местом жизни" агента;
- реальная среда работы — это операционная система пользователя или сервера;
- агент живёт как процесс, может порождать другие процессы и связываться с ними через файловую систему, сеть и IPC;
- с ростом автономности система естественно движется от UI и разовых команд к OS-level orchestration.

Различаются конкретные продукты, флаги, SDK и политические слои безопасности.
Но сам переход:

`чат -> терминал -> headless -> демон -> организация`

по идеологии одинаков для обоих терминальных агентов.

## Два уровня: интерфейс и пространство ОС

### Терминал как интерфейс

Терминал — это программа, которая принимает текстовые команды от пользователя и передаёт их операционной системе. Это один из способов взаимодействия с компьютером, наряду с графическим интерфейсом (GUI). Терминал не является частью ОС в том смысле, в каком являются ядро, файловая система или менеджер процессов. Это окно, через которое вы видите и управляете тем, что происходит внутри.

Когда вы запускаете Claude Code командой `claude` в терминале, вы инициализируете процесс. Этот процесс получает права текущего пользователя ОС и доступ ко всем ресурсам, которые этому пользователю разрешены.

### Внутреннее пространство операционной системы

Внутри ОС одновременно работают сотни процессов: ядро управляет памятью и устройствами, сетевой стек обрабатывает соединения, файловые системы обеспечивают доступ к данным, службы и демоны выполняют фоновые задачи. Каждый процесс имеет свой идентификатор (PID), область памяти, дескрипторы файлов, сетевые соединения. Процессы могут порождать дочерние процессы, обмениваться данными через сокеты, пайпы, shared memory, сигналы.

Терминал — это лишь один из множества процессов в этом пространстве. Когда агент создаёт новый процесс (например, запускает скрипт или демон), этот процесс существует в пространстве ОС наравне со всеми остальными. Он не привязан к терминалу. Он привязан к операционной системе.

## Как агент получает доступ к ОС

### Точка входа — терминал

Claude Code запускается как обычный процесс пользователя. В момент запуска он получает доступ ко всему, что доступно этому пользователю: файловая система, сетевые интерфейсы, установленные программы, переменные окружения, права на запуск и управление процессами. Агент использует встроенный инструмент Bash для выполнения команд — это эквивалент того, как пользователь вводит команды вручную, но делает это программно.

### Что доступно агенту

Через Bash агент может выполнять всё, что может пользователь в терминале.

**Файловая система:** чтение, создание, редактирование, удаление файлов и директорий в пределах прав пользователя. Это включает конфигурационные файлы, логи, базы данных, исходный код, медиафайлы — всё, что лежит на диске.

**Процессы:** запуск новых процессов (`python script.py`, `node server.js`, `docker run ...`), мониторинг существующих (`ps`, `top`, `lsof`), отправка сигналов (`kill`, `killall`), управление приоритетами (`nice`, `renice`). Агент видит дерево процессов и может взаимодействовать с любым процессом, к которому у пользователя есть доступ.

**Сеть:** отправка HTTP-запросов (`curl`, `wget`), работа с сокетами, проверка сетевых соединений (`netstat`, `ss`), DNS-запросы, взаимодействие с любыми API через сеть.

**Установка программ:** `pip install`, `npm install`, `apt install` (с sudo, если есть права), `brew install`. Агент может расширять свой собственный инструментарий, устанавливая нужные библиотеки и утилиты.

**Системные службы:** создание и управление cron-задачами, launchd-сервисами (macOS), systemd-юнитами (Linux). Это позволяет агенту создавать сущности, которые переживут завершение его собственного процесса.

## Порождение процессов: от одного агента к агентной архитектуре

### Агент как порождающий процесс

Ключевое свойство процесса в ОС — он может порождать дочерние процессы. Claude Code использует это свойство на нескольких уровнях.

**Первый уровень: выполнение команд.** Каждая bash-команда — это дочерний процесс. Когда агент выполняет `python analyze.py`, ОС создаёт новый процесс с собственным PID, памятью, потоками ввода-вывода. Агент ждёт завершения и читает результат.

**Второй уровень: фоновые процессы.** Агент может запустить процесс в фоне: `python server.py &`. Такой процесс продолжает работать, даже когда агент перешёл к следующей задаче. Агент может позже проверить его состояние, прочитать логи, остановить или перезапустить.

**Третий уровень: демоны и службы.** Агент может создать systemd-сервис или launchd plist — процесс, управляемый операционной системой. Такой процесс автоматически запускается при загрузке ОС, перезапускается при сбое, логируется системными средствами. Он полностью независим от Claude Code — существует в пространстве ОС как самостоятельная сущность.

**Четвёртый уровень: порождение других агентов.** Агент может запустить другой экземпляр Claude Code в headless-режиме: `claude -p "выполни задачу X"`. Этот второй агент — отдельный процесс со своим контекстом, своим набором инструментов, своей задачей. Первый агент может запустить десять таких экземпляров параллельно, каждый с уникальным промптом.

### Мультипликация агентов

Вот где возникает агентная архитектура. Один агент, получив доступ к ОС, может:

1. Создать скрипт-оркестратор (Python, Bash, Node.js), который управляет запуском нескольких агентов.
2. Каждому агенту задать свою миссию через промпт: один анализирует логи, другой проверяет безопасность кода, третий обновляет документацию.
3. Настроить межагентное взаимодействие через файловую систему (общие файлы), сокеты, или очередь сообщений.
4. Создать систему мониторинга: скрипт, который проверяет, работают ли все агенты, перезапускает упавших, собирает результаты.
5. Обернуть всё это в systemd/launchd, чтобы архитектура пережила перезагрузку компьютера.

Результат — организация агентов, функционирующая на уровне ОС, где каждый агент является процессом (или группой процессов), а координация осуществляется через стандартные механизмы межпроцессного взаимодействия.

## Agent SDK: программный уровень оркестрации

### От bash-скриптов к программному контролю

Описанная выше архитектура может быть построена через bash-скрипты и headless-вызовы `claude -p`. Но Agent SDK предоставляет более элегантный и контролируемый способ.

Agent SDK — это библиотека для Python и TypeScript, которая оборачивает возможности Claude Code в программный API. Вместо вызова `claude -p` из bash вы создаёте агента как объект в коде:

```python
async for message in query(
    prompt="Проанализируй логи за последние 24 часа",
    options=ClaudeAgentOptions(
        allowed_tools=["Read", "Grep", "Bash"],
        max_turns=20,
        system_prompt="Ты — агент мониторинга. Ищи аномалии."
    )
):
    process_result(message)
```

### Преимущества программного уровня

**Типизированный контроль.** Вы точно определяете, какие инструменты доступны каждому агенту. Один агент может только читать файлы (Read, Grep, Glob). Другой — только выполнять определённые команды. Третий — имеет полный доступ. Это реализует принцип наименьших привилегий.

**Субагенты с изоляцией.** Agent SDK позволяет основному агенту порождать субагентов, каждый из которых работает в изолированном контексте:

```python
agents={
    "log-analyzer": AgentDefinition(
        description="Анализ логов на аномалии",
        tools=["Read", "Grep"],  # только чтение
        model="haiku"  # быстрая модель для рутины
    ),
    "security-scanner": AgentDefinition(
        description="Проверка безопасности",
        tools=["Read", "Grep", "Bash"],  # может запускать сканеры
        model="opus"  # мощная модель для сложного анализа
    )
}
```

**Кастомные инструменты.** Через MCP-серверы агенты получают доступ к произвольным системам: базам данных, API, очередям сообщений, мессенджерам. Каждый инструмент — это функция, которую агент вызывает по необходимости:

```python
@tool("send_alert", "Отправить оповещение в Telegram", {"message": str})
async def send_alert(args):
    telegram_api.send(chat_id=ADMIN_CHAT, text=args["message"])
    return {"content": [{"type": "text", "text": "Оповещение отправлено"}]}
```

**Хуки для контроля.** Перехват любого действия агента до или после выполнения. Логирование, блокировка опасных операций, аудит — всё программируется:

```python
async def safety_hook(tool_name, input_data, context):
    if tool_name == "Bash" and "rm" in input_data.get("command", ""):
        return PermissionResultDeny("Удаление запрещено политикой")
    return PermissionResultAllow()
```

### Развёртывание как сервис

Программа, написанная с Agent SDK, — это обычный Python/TypeScript-процесс. Его можно:

- Запустить как systemd-сервис на сервере.
- Обернуть в Docker-контейнер и развернуть в облаке.
- Подключить к очереди задач (Redis, RabbitMQ, SQS) для обработки входящих запросов.
- Масштабировать горизонтально: несколько экземпляров на нескольких машинах.

Это уже не "агент в терминале" — это агентная инфраструктура уровня production-сервиса.

## Уровни автономности: от диалога к полной автономии

### Уровень 0: Диалог (Chat)

Пользователь задаёт вопрос — модель отвечает текстом. Никакого доступа к ОС. Никаких действий за пределами генерации текста. Это GPT-чат, Claude Chat, любой текстовый интерфейс.

### Уровень 1: Песочница (Cowork)

Агент имеет доступ к изолированной виртуальной машине. Может выполнять команды, создавать файлы, запускать скрипты — но только внутри песочницы. Не видит основную ОС пользователя. Не может создавать системные процессы. Процессы внутри песочницы умирают при завершении сессии.

### Уровень 2: Терминал (Claude Code CLI)

Агент получает доступ к реальной ОС через терминал. Может управлять файлами и процессами пользователя. Но работает интерактивно — пока терминал открыт и пользователь наблюдает. Режимы разрешений (Ask, acceptEdits) создают контроль: агент спрашивает перед опасными действиями.

### Уровень 3: Headless-режим

Агент запускается без интерфейса: `claude -p "задача"`. Выполняет задачу автономно и завершается. Может быть встроен в cron, скрипт, пайплайн. Пользователь не наблюдает за процессом в реальном времени — только видит результат. Это первый уровень настоящей автономности.

### Уровень 4: Демон / Служба

Агент (через Agent SDK или скрипт-обёртку) работает как фоновый процесс ОС. Не зависит от терминала, от приложения, от присутствия пользователя. Слушает очередь задач, обрабатывает события, реагирует на триггеры. Перезапускается автоматически при сбое. Это серверный уровень автономности.

### Уровень 5: Агентная организация

Несколько агентов работают параллельно, каждый со своей ролью, набором инструментов и областью ответственности. Оркестратор (тоже агент или скрипт) распределяет задачи, собирает результаты, принимает решения о маршрутизации. Агенты могут порождать субагентов для подзадач. Система функционирует на уровне ОС как совокупность связанных процессов.

## Ограничения и правила

### Права доступа

Агент работает от имени пользователя, запустившего его. Он не может сделать больше, чем может этот пользователь. Если у пользователя нет sudo — агент не установит системный пакет. Если файл принадлежит root — агент его не прочитает. Стандартная модель безопасности Unix работает как ограничитель.

### Режимы разрешений

Claude Code реализует собственную систему разрешений поверх прав ОС. Режим Ask — агент спрашивает перед каждым действием. Режим acceptEdits — автоматически правит файлы, но спрашивает перед bash-командами. Режим dontAsk (bypass) — полная автономия, агент делает всё без вопросов. Выбор режима определяет степень доверия: от полного контроля до полной автономии.

### Контроль через хуки

Даже в автономном режиме можно установить программные ограничения через хуки. Например: запретить удаление файлов, разрешить только определённые bash-команды, логировать все действия для аудита. Хуки — это программный слой контроля между агентом и ОС.

### Бюджет и лимиты

Agent SDK позволяет задать ограничения: максимальное количество шагов (`max_turns`), бюджет в долларах (`max_budget_usd`), таймауты. Это предотвращает ситуации, когда агент зацикливается или тратит неконтролируемое количество ресурсов.

### Изоляция через контейнеры

Для production-развёртывания агентов рекомендуется использовать контейнеры (Docker, gVisor, Firecracker). Каждый агент работает в своём контейнере с ограниченными ресурсами и правами. Даже если агент попытается выполнить деструктивное действие — оно затронет только контейнер, не хост-систему.

## Практическая архитектура: пример

Представим задачу: автоматический мониторинг и обслуживание веб-приложения.

**Оркестратор** — Python-скрипт, работающий как systemd-сервис. Раз в час запускает цикл проверки.

**Агент-монитор** — запускается оркестратором через Agent SDK. Проверяет логи приложения, метрики сервера, статус-коды HTTP. Инструменты: Read, Grep, Bash (ограничен командами `curl`, `docker logs`, `df`, `free`). Если находит аномалию — записывает отчёт в файл.

**Агент-диагност** — запускается оркестратором, только если монитор нашёл аномалию. Читает отчёт монитора, анализирует логи глубже, определяет причину. Инструменты: Read, Grep, Bash (ограничен командами анализа). Формирует диагноз и рекомендацию.

**Агент-исполнитель** — запускается, только если диагноз содержит автоматически исправимую проблему (например, переполненный диск, упавший контейнер). Инструменты: Bash (ограничен разрешённым списком команд: `docker restart`, `journalctl`, `rm` только в директории логов). Выполняет исправление.

**Агент-нотификатор** — кастомный инструмент через MCP, отправляет сообщение в Telegram или Slack с результатами цикла.

Каждый агент — отдельный процесс со своими правами, своей задачей, своим бюджетом токенов. Оркестратор управляет последовательностью и передачей данных между ними. Всё работает на уровне ОС, без участия человека, 24/7.

## Вывод

Подлинная автономность AI-агента реализуется не в чат-интерфейсе и не в графическом приложении. Она реализуется на уровне операционной системы, где агент существует как процесс (или совокупность процессов) с доступом к ресурсам компьютера.

Терминал — это лишь точка входа, через которую агент попадает в пространство ОС. Всё, что он создаёт после этого — скрипты, демоны, службы, другие агенты — живёт в пространстве ОС и подчиняется её правилам: управление процессами, права доступа, межпроцессное взаимодействие, файловая система.

Разница между "Claude в чате" и "агентной организацией на уровне ОС" — это разница между разговором с экспертом и наймом команды, которая работает автономно, по заданным правилам, с распределением ролей и ответственности. Первое — интерфейс. Второе — инфраструктура.
