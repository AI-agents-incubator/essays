# Векторизация: когда не нужна, когда достаточно open-source, когда пора платить

## Контекст этого документа

Этот документ — результат семичасовой дискуссии о том, в какой момент применять векторизацию и какую технологию использовать. Он не претендует на полноту обзора рынка. Его задача — дать практическую рамку принятия решений для команды, которая строит системы с ИИ и работает с базами знаний.

---

## Что такое векторизация и зачем она вообще нужна

Векторизация (embedding) — это преобразование текста в массив чисел (вектор), который отражает «смысл» текста. Два текста с похожим смыслом получают близкие векторы, даже если написаны разными словами.

Это нужно для одной конкретной задачи: **поиск по смысловой близости**. Когда пользователь спрашивает «как решить проблему с доступом», а в базе лежит документ «устранение ошибок авторизации» — обычный текстовый поиск не найдёт совпадения. Векторный — найдёт.

Сама по себе векторизация — это не RAG-система. Это один компонент внутри неё. RAG = retrieval (поиск релевантных фрагментов) + augmented generation (передача найденного в LLM для генерации ответа). Векторизация отвечает только за первую часть — за то, как именно ищутся похожие фрагменты.

## Voyage AI: что это и чем отличается от open-source моделей

### Voyage AI

Voyage AI (приобретён MongoDB) — коммерческий сервис, предоставляющий embedding-модели через API. Отправляешь текст — получаешь вектор. Текущая линейка: Voyage 4, voyage-3.5, voyage-multimodal-3.5. Размерность векторов — до 1024. Контекстное окно — до 32K токенов. Есть специализированные модели для кода, юриспруденции, финансов. Среди клиентов — Anthropic, Databricks, Snowflake.

### multilingual-e5-small

Open-source модель от Microsoft (семейство E5). Размерность — 384. Контекст — 512 токенов. Работает на 100+ языках. Запускается локально через библиотеку `sentence-transformers` за пять строк кода. Бесплатна, не требует API-ключей и внешних зависимостей.

### Ключевые отличия

| Параметр | multilingual-e5-small | Voyage AI |
|---|---|---|
| Размерность вектора | 384 | до 1024 |
| Контекстное окно | 512 токенов | до 32K токенов |
| Качество на сложных запросах | Базовое | Высокое |
| Специализация по доменам | Нет | Финансы, право, код |
| Стоимость | Бесплатно | Оплата за токены |
| Зависимость от внешнего API | Нет | Да |
| Запуск | Локально / Edge Function | Только через API |
| Fine-tuning под свои данные | Возможен, но требует экспертизы | Предлагается как сервис |

**Практический смысл различий:** e5-small хорошо справляется с простыми паттернами — когда запрос и ответ сформулированы похоже, предметная область узкая, а длина документов умеренная. Voyage AI даёт преимущество на сложных семантических запросах: когда формулировки сильно расходятся, терминология неоднородна, документы длинные, а домен специфичен.

## Три зоны: когда векторизация не нужна, когда хватит open-source, когда платить

### Зона 1. Векторизация не нужна — улучшай данные

Это самая важная и самая недооценённая зона.

Во многих системах проблема качества ответов связана не с тем, что «поиск недостаточно умный», а с тем, что данные хранятся в сыром виде. После созвона в системе остаётся расшифровка, пара заметок, комментарий в чате и обновление статуса в трекере. Потом команда пытается решить это векторной БД: «давайте всё проиндексируем, и модель разберётся». Обычно не разберётся.

**Признаки того, что вы в этой зоне:**

- Основная ценность — в структурных сущностях (клиенты, задачи, статусы, сделки, документы).
- Чаще спрашивают «что актуально» и «какая последняя версия», а не «что похоже».
- Запросы детерминированы: пользователь знает, что ищет, и может назвать сущность.
- Данных умеренно (сотни-тысячи документов, а не сотни тысяч).
- Главная проблема — не поиск, а бардак: нет source of truth, нет разделения сырого текста и канонического знания, нет нормализации.

**Что делать вместо векторизации:**

- Описать сущности и их связи.
- Отделить сырой текст (расшифровки, заметки) от нормализованного знания (решения, статусы, факты).
- Построить retrieval на SQL + полнотекстовом поиске (FTS5 в SQLite, `tsvector` в PostgreSQL / Supabase).
- Добавить alias-таблицы для синонимов, ранжирование по свежести и типу источника.
- Ввести тестовый набор запросов и измерить, где система промахивается.

**Ключевой принцип:** пока не доказано, что простая архитектура не справляется, RAG — это дорогой способ замаскировать бардак в данных.

### Зона 2. Векторизация нужна — хватает open-source

Вы перешли в эту зону, если на реальном тестовом наборе запросов видно, что SQL + FTS системно не находят релевантные материалы, и причина именно в недостатке семантического поиска, а не в плохой структуре данных.

**Признаки:**

- Пользователи формулируют запросы свободно, не зная точных терминов.
- FTS промахивается на синонимах и перефразировках.
- Нужен поиск «похожих случаев», а не конкретных документов.
- Данных уже достаточно много, но предметная область относительно однородна.
- Запросы и документы — на одном-двух языках, терминология не слишком специфична.

**Что использовать:**

| Модель | Размерность | Контекст | Особенности |
|---|---|---|---|
| `multilingual-e5-small` | 384 | 512 | Лёгкая, мультиязычная, хороша для старта |
| `multilingual-e5-base` | 768 | 512 | Точнее, но тяжелее |
| `multilingual-e5-large` | 1024 | 512 | Ещё точнее, требует GPU для комфортной работы |
| `all-MiniLM-L6-v2` | 384 | 256 | Быстрая, только английский |
| `bge-m3` (BAAI) | 1024 | 8192 | Мультиязычная, длинный контекст, одна из лучших open-source |
| `nomic-embed-text` | 768 | 8192 | Длинный контекст, хорошее качество |

Все модели запускаются локально через `sentence-transformers` (Python) или через Ollama. Бесплатны, без API-ключей.

**Важно:** при переходе от одной embedding-модели к другой нужно перевекторизировать всю базу. Векторы разных моделей несовместимы — нельзя смешивать 384-мерные от e5-small с 1024-мерными от bge-m3.

**Пример кода (5 строк):**

```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer('intfloat/multilingual-e5-small')
vector = model.encode("Ваш текст для векторизации")
# vector — массив из 384 чисел, готовый для записи в Supabase (pgvector)
```

### Зона 3. Нужна коммерческая модель (Voyage AI, OpenAI Embeddings и др.)

Переход в эту зону оправдан, когда open-source модели измеримо не дотягивают по качеству, и разница влияет на бизнес-результат.

**Признаки:**

- Предметная область узкоспециализирована (юриспруденция, медицина, финансы, код), и общие модели плохо понимают доменную терминологию.
- Корпус большой, лингвистически неровный: много синонимии, жаргона, сокращений, разных стилей.
- Документы длинные (десятки страниц), и модель с контекстом 512 токенов теряет смысл при нарезке на мелкие чанки.
- Качество retrieval измеряется на бенчмарке, и разница между open-source и коммерческой моделью составляет значимые проценты recall.
- Есть ресурс на поддержку: пайплайн индексации, chunking strategy, пересчёт эмбеддингов, мониторинг качества.
- Продукт уже монетизируется, и стоимость API — это операционный расход, а не эксперимент.

**Варианты:**

| Сервис | Размерность | Контекст | Цена (ориентир) |
|---|---|---|---|
| Voyage AI (voyage-3.5) | до 1024 | до 32K | ~$0.06 / 1M токенов |
| OpenAI (text-embedding-3-small) | 1536 | 8191 | $0.02 / 1M токенов |
| OpenAI (text-embedding-3-large) | 3072 | 8191 | $0.13 / 1M токенов |
| Google (text-embedding-004) | 768 | 2048 | Зависит от плана |
| Cohere (embed-v3) | 1024 | 512 | $0.10 / 1M токенов |

**Когда Voyage AI конкретно:** если нужна специализация по домену (финансы, право, код), длинный контекст (32K), или вы уже в экосистеме MongoDB (Atlas Vector Search).

**Когда OpenAI Embeddings:** если уже используете OpenAI API для генерации — проще держать одного вендора. Хорошее соотношение цена/качество на text-embedding-3-small.

## Как это связано с Anthropic / Claude

У Anthropic (Claude) на данный момент **нет собственного embedding API**. Claude — генеративная модель, она отвечает на вопросы, но не превращает текст в вектор.

Поэтому в любой RAG-системе на базе Claude всегда два «работника»:

1. **Embedding-модель** (Voyage AI / OpenAI / open-source) — превращает текст в вектор для записи в базу и для поиска.
2. **Claude** — получает найденные фрагменты и формулирует ответ.

Это разные задачи, разные модели, разные расходы. Выбор embedding-модели не зависит от выбора LLM для генерации.

## Практическая рамка принятия решения

### Оставайся без векторизации, если:

- данные по сути табличные (сущности, статусы, связи);
- нужна точность по полям и фильтрам, а не «похожее»;
- главная проблема — отсутствие структуры, а не слабый поиск;
- нет тестового набора запросов, на котором можно измерить провал;
- SQL + FTS закрывают большинство кейсов.

### Используй open-source (e5-small и выше), если:

- есть устойчивый спрос на поиск по смыслу;
- FTS системно промахивается на синонимах и перефразировках;
- предметная область не слишком специфична;
- бюджет ограничен или нет смысла платить за API;
- нужна автономность (работа без внешних зависимостей).

### Переходи на коммерческую модель, если:

- open-source измеримо не дотягивает по recall на бенчмарке;
- домен узкоспециализирован и требует доменных моделей;
- документы длинные и нужен контекст >512 токенов на чанк;
- продукт монетизируется и расходы на API оправданы;
- есть ресурс на поддержку инфраструктуры vectorization pipeline.

## Главный вывод

Сильная система памяти начинается не с эмбеддингов. Она начинается с того, что данные перестают быть просто текстом.

Последовательность: **структура данных → SQL + FTS → тестовый набор запросов → диагностика провалов → и только тогда векторизация**.

На каждом следующем этапе — от open-source к коммерческой модели — решение принимается не по ощущению «так современнее», а по измеримому разрыву качества на конкретных запросах.
