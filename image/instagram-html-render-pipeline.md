# Instagram HTML → PNG Pipeline

## Идея

Вместо генерации каждой Instagram-картинки нейросетью с нуля использовать набор заранее подготовленных HTML/CSS-шаблонов.

Модель отвечает не за финальный визуальный рендер, а за содержание и выбор параметров шаблона. Само изображение создаётся детерминированно кодом.

Базовая цепочка:

**Исходный текст → анализ моделью → структурированный JSON → HTML-шаблон → Playwright/Puppeteer → PNG → публикация в Instagram**

---

## Почему этот подход интересен

Главное преимущество — управляемость.

Генеративная картинка каждый раз немного непредсказуема. Даже хороший prompt не гарантирует одинаковую композицию, типографику, визуальную иерархию и брендовый стиль.

HTML/CSS, наоборот, позволяет заранее определить:

- размер холста;
- расположение элементов;
- типографику;
- фон;
- декоративные элементы;
- изображения;
- логотип;
- отступы;
- допустимую длину текста;
- варианты композиции.

После того как шаблон визуально отлажен, его рендер практически детерминирован.

---

## Размер и формат

Поскольку конечный потребитель — Instagram, нет необходимости строить универсальную адаптивную систему.

Можно использовать фиксированные размеры, например:

- `1080 × 1080` — квадрат;
- `1080 × 1350` — вертикальный пост 4:5;
- `1080 × 1920` — Stories / Reels cover.

Для каждого формата можно иметь отдельный набор шаблонов.

---

## Шаблоны

На первом этапе достаточно сделать примерно 5–10 шаблонов.

Например:

1. Большая цитата на фоне.
2. Заголовок + короткий текст.
3. Текст + декоративная иллюстрация.
4. Минималистичная типографическая карточка.
5. Карточка с крупным номером или тезисом.
6. Split-layout: изображение + текст.
7. Темный editorial-style шаблон.
8. Светлый журнальный шаблон.
9. Абстрактный фон + текст.
10. Карточка серии / рубрики.

Позже количество шаблонов можно увеличивать практически без изменения архитектуры pipeline.

---

## Важный принцип

Модель **не должна генерировать HTML при каждом посте**.

Лучше держать HTML/CSS-шаблоны как обычный код.

Модель получает исходный текст и возвращает только структурированные данные.

Например:

```json
{
  "template": "editorial-dark-03",
  "headline": "The future is already here",
  "body": "We just distribute it unevenly.",
  "category": "FUTURE",
  "accent": "01",
  "background": "gradient-07"
}
```

Дальше код подставляет эти значения в соответствующий HTML-шаблон.

---

## Ограничение длины текста

Это одна из сильных сторон подхода.

Не нужно пытаться создавать универсальную систему автоматического масштабирования текста.

Для каждого поля шаблона можно заранее определить диапазон.

Например:

```text
headline: 30–70 символов
body: 150–230 символов
category: до 20 символов
```

Поскольку текст создаёт модель, ей можно прямо дать ограничения:

> Generate a headline between 40 and 60 characters and body text between 170 and 210 characters.

Таким образом модель сама адаптирует содержание под дизайн.

Если текст не проходит валидацию, можно просто сделать повторный запрос.

## Архитектура

### 1. Source Text

На вход приходит исходный текст:

- пост;
- статья;
- заметка;
- цитата;
- длинный текст;
- идея.

### 2. AI Analysis

Модель анализирует текст и определяет:

- главный тезис;
- эмоциональный тон;
- категорию;
- подходящий визуальный шаблон;
- headline;
- body;
- дополнительные параметры.

### 3. Structured Output

Модель возвращает JSON по заранее заданной schema.

Например:

```json
{
  "template_id": "quote_04",
  "headline": "...",
  "body": "...",
  "theme": "dark",
  "image_id": "background_12"
}
```

Желательно использовать Structured Outputs / JSON Schema, чтобы модель физически не могла вернуть произвольную структуру.

### 4. Template Engine

Код берёт `template_id` и загружает соответствующий HTML/CSS-шаблон.

Например:

```text
/templates
  quote-01.html
  quote-02.html
  editorial-01.html
  editorial-02.html
  image-text-01.html
```

Или шаблоны можно реализовать React-компонентами.

### 5. Data Injection

JSON подставляется в шаблон.

Например:

```html
<h1>{{headline}}</h1>
<p>{{body}}</p>
```

или через React props.

### 6. Browser Rendering

HTML открывается в headless browser.

Подходящие инструменты:

- Playwright;
- Puppeteer.

Например, Playwright запускает Chromium, открывает страницу с фиксированным viewport и ждёт загрузки шрифтов и изображений.

### 7. Screenshot

После загрузки страницы делается screenshot:

```text
1080 × 1350 PNG
```

Это и есть готовый Instagram asset.

### 8. Publication

PNG вместе с caption передаётся дальше в существующий pipeline публикации Instagram.

## Где работает Playwright

Playwright не работает «внутри модели».

Он запускается в обычном вычислительном окружении.

Например:

### Вариант A — локально

Node.js + Playwright на локальном компьютере.

Подходит для разработки и тестирования.

### Вариант B — Docker

Отдельный Docker container:

```text
Node.js
Playwright
Chromium
Templates
Fonts
```

Это хороший вариант для production.

### Вариант C — сервер

Обычный VPS / cloud instance.

Pipeline запускается по API или job queue.

### Вариант D — serverless

Технически возможно, но headless Chromium иногда создаёт лишние сложности из-за размера пакета, cold start и ограничений окружения.

Для первой версии проще Docker или обычный сервер.

## Работа с изображениями

Фоновые изображения, texture, illustrations и decorative assets можно подготовить заранее.

Например:

```text
/assets
  backgrounds/
  textures/
  illustrations/
  icons/
  logos/
```

Это позволяет один раз создать качественные визуальные элементы, а затем использовать их сотни раз.

Можно также заранее сгенерировать AI-изображения и включить их в библиотеку assets.

Получается интересная гибридная система:

**AI генерирует визуальные материалы редко → deterministic template использует их много раз.**

## Как выбирать шаблон

Есть несколько вариантов.

### Вариант 1 — модель выбирает сама

В prompt модели передаётся описание доступных шаблонов.

Она возвращает:

```json
{
  "template_id": "editorial_05"
}
```

### Вариант 2 — код выбирает шаблон

Например по категории:

```text
quote → quote templates
philosophy → editorial templates
business → diagram templates
story → image templates
```

### Вариант 3 — гибрид

Модель определяет категорию, а код случайно выбирает один из 3–5 допустимых шаблонов этой категории.

Этот вариант может дать хороший баланс между разнообразием и контролем.

---

## Variations

Чтобы лента не выглядела одинаково, шаблон необязательно должен быть полностью фиксирован.

У него могут быть параметры:

```json
{
  "layout": 2,
  "background": 7,
  "font_scale": "large",
  "alignment": "left",
  "accent": "blue"
}
```

Но набор вариантов остаётся конечным и протестированным.

Это создаёт ощущение разнообразия без генеративного хаоса.

---

## Валидация

Перед рендером желательно проверять:

- длину headline;
- длину body;
- отсутствие пустых полей;
- допустимый template_id;
- существование asset;
- допустимые параметры шаблона.

Если данные не проходят проверку, модель получает retry.

---

## Дополнительная визуальная проверка

После рендера PNG можно при желании снова передавать vision-модели.

Она может проверить:

- не обрезан ли текст;
- нормальна ли визуальная иерархия;
- нет ли странных переносов;
- читается ли карточка;
- нет ли визуальных ошибок.

То есть можно получить pipeline:

```text
Text
↓
AI content generation
↓
JSON
↓
HTML
↓
Playwright
↓
PNG
↓
AI visual QA
↓
Publish
```

Но для MVP visual QA, вероятно, не нужен.

## MVP

Для первого рабочего прототипа достаточно:

1. Сделать 3 HTML-шаблона.
2. Использовать размер `1080 × 1350`.
3. В каждом шаблоне иметь `headline` и `body`.
4. Задать жёсткие ограничения длины.
5. Сделать JSON schema для ответа модели.
6. Подставлять JSON в шаблон.
7. Рендерить через Playwright.
8. Сохранять PNG.
9. Посмотреть 20–30 автоматически созданных карточек.
10. Исправить шаблоны там, где появляются визуальные проблемы.

Только после этого имеет смысл добавлять десятки шаблонов.

## Основная идея архитектуры

Здесь полезно разделить AI и deterministic code.

### AI отвечает за:

- понимание текста;
- смысл;
- сокращение;
- headline;
- copy;
- категоризацию;
- выбор подходящего визуального сценария.

### Код отвечает за:

- layout;
- typography;
- размеры;
- изображения;
- цвета;
- композицию;
- рендер;
- PNG;
- публикацию.

То есть:

> **AI принимает творческие решения, а код гарантирует визуальное исполнение.**

Именно это делает систему одновременно гибкой и управляемой.

---

## Почему этот подход может оказаться лучше полной генерации изображений

Генерация изображения с нуля имеет смысл, когда уникальная иллюстрация — центральная часть контента.

Но если главная задача — визуально оформлять идеи, тезисы, цитаты и короткие тексты, HTML-render pipeline даёт:

- более стабильное качество;
- намного лучший контроль typography;
- бренд-консистентность;
- дешёвый рендер;
- быстрые итерации;
- повторяемость;
- простое A/B-тестирование;
- возможность иметь десятки визуальных форматов.

Поэтому логичный вариант архитектуры:

**HTML templates — основной режим.**

**AI image generation — дополнительный режим для постов, где уникальная иллюстрация действительно добавляет ценность.**
