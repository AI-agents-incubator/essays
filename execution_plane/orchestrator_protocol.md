# Orchestrator Protocol

> Версия файла: `v1.0`
> Дата версии: `2026-03-17`
> Тип документа: `execution protocol`

## Назначение

Этот документ описывает, как execution plane связывает:

- `control_plane`
- paused runtime sessions
- headless CLI launch / resume

## Базовая логика

Для каждого runtime оркестратор читает:

1. `RUNTIME_STATUS.md`
2. `OBSERVER_DIRECTIVE.md`
3. `RUNTIME_ACK.md`

После этого он принимает техническое решение:

- ничего не делать;
- запустить runtime;
- резюмировать runtime;
- ждать завершения уже идущего процесса.

## Когда оркестратор ничего не делает

- если `action = hold` и runtime уже подтвердил директиву;
- если runtime уже запущен;
- если директива не активна;
- если директива уже была принята и сейчас нет оснований для нового запуска.

## Когда оркестратор запускает runtime

- если есть новая активная директива;
- если runtime ещё не подтвердил эту директиву;
- если по типу директивы требуется активная работа:
  - `continue_with_next_run`
  - `repair_current_state`
  - `prepare_comparison`
  - `human_review_required` при необходимости донести команду до runtime

## Почему используется resume, а не новый старт

Потому что текущая архитектура уже построена вокруг существующих сессий runtime.

Значит правильнее:

- не создавать новые разговоры без необходимости;
- а резюмировать самые последние сессии в соответствующих runtime-директориях.

Для этого используются:

- `codex exec resume --last`
- `claude --continue --print`

## Что пишет оркестратор

Оркестратор сам не меняет `control_plane`-решения.

Он пишет только техническое состояние запуска в свои служебные файлы:

- process state
- PID
- log files
- last message snapshots

Эти файлы являются локальным operational trace execution layer.
