# Plug-and-Play Agent Organization: User Flow and High-Level Product Spec

> Версия файла: `v1.0`
> Дата версии: `2026-03-18`
> Тип документа: `high-level product spec`

## Назначение документа

Этот документ формализует конечный целевой сценарий с точки зрения пользователя.

Он отвечает на вопрос:

**что именно должен делать пользователь, что должна делать система, и по каким признакам понятно, что plug-and-play формат действительно достигнут.**

## Контекст

Сейчас scope осознанно сужен:

**агентная организация рассматривается как автономная компания по разработке приложений.**

То есть она должна уметь принимать проектный запрос, превращать его в управляемую разработку и дальше работать по организованному pipeline с минимальным вмешательством человека.

## Целевой пользователь

Целевой пользователь этого формата:

- не обязан быть разработчиком;
- не обязан знать внутреннюю архитектуру Codex или Claude Code;
- не обязан вручную строить роли, граф задач и операционные правила;
- хочет описать, что ему нужно, и передать дальнейшую организацию работы системе.

## Главная цель продукта

Сделать такой формат работы, при котором пользователь:

1. создаёт папку проекта;
2. разворачивает starter kit;
3. описывает своё намерение;
4. передаёт управление агентной организации;
5. дальше получает не хаотический чат, а организованный процесс разработки.

## Конечный результат с точки зрения пользователя

Пользователь должен получить не набор разрозненных markdown-файлов, а работающую организационную оболочку, в которой:

- уже есть структура агентной организации;
- уже есть bootstrap path;
- уже есть project input format;
- уже есть рамки автономности;
- уже есть правила эскалации;
- уже есть путь от project request к product brief, engineering spec, task graph и execution.

## User Flow

### Stage 1. Создание папки проекта

Пользователь создаёт новую папку.

Эта папка может быть:

- полностью пустой;
- уже содержать существующий проект;
- содержать legacy codebase.

Система должна уметь работать в обоих режимах:

- `greenfield`
- `overlay on existing project`

## Stage 2. Развёртывание starter kit

Пользователь запускает installable starter scaffold.

Результат:

- в проекте появляется `agent_org/`;
- в проекте появляется `project_input/`;
- в проекте появляется `START_HERE.md`;
- в проекте появляются минимальные policies, bootstrap и рабочие шаблоны.

На этом этапе должны быть также готовы:

- глобальные runtime baselines;
- project-level организационные файлы;
- стартовый bootstrap path для handoff к агентной организации.

## Stage 3. Нормализация пользовательского намерения

Пользователь редко умеет сразу писать хороший структурированный входной файл.

Поэтому правильный продуктовый flow должен допускать два режима:

### Mode A. Пользователь сам заполняет structured input

Он заполняет:

- `project_input/PROJECT_REQUEST.md`
- при необходимости `project_input/PROJECT_CONSTRAINTS.md`

### Mode B. Система помогает нормализовать свободное описание

Пользователь пишет свою идею свободным текстом, а система:

- задаёт минимум уточняющих вопросов;
- превращает свободный текст в нормализованный входной артефакт;
- только после этого передаёт его агентной организации как официальный input.

Это важное требование.

Иначе качество старта будет слишком сильно зависеть от умения пользователя писать хорошие промпты.

## Stage 4. Handoff к агентной организации

После появления нормализованного входного артефакта начинается настоящий handoff.

Агентная организация читает:

1. `START_HERE.md`
2. `project_input/PROJECT_REQUEST.md`
3. `project_input/PROJECT_CONSTRAINTS.md`
4. bootstrap, charter и policy files

После этого она не должна сразу "писать код".

Она должна пройти обязательную последовательность:

1. подтвердить понимание запроса;
2. определить, достаточно ли информации;
3. при необходимости запустить discovery-phase;
4. сформировать product brief;
5. сформировать engineering spec;
6. построить task graph;
7. построить execution plan;
8. только после этого перейти к исполнению.

## Stage 5. Discovery Phase

Discovery-phase должна быть не обязательной всегда, а условной.

Она запускается только если:

- запрос слишком размыт;
- отсутствуют критически важные ограничения;
- неясен scope;
- неясно, на чём именно строить execution plan.

Discovery-phase может включать:

- уточняющие вопросы;
- анализ существующего проекта;
- сбор контекста по коду, документам и структуре;
- выделение неизвестных и рисков;
- первичную оценку масштаба.

## Stage 6. Организационное разворачивание

После discovery или сразу после intake организация должна развернуть собственную внутреннюю работу.

Это включает:

- создание ролей;
- распределение ответственности;
- построение task graph;
- декомпозицию на work orders;
- при необходимости распараллеливание;
- определение точек синхронизации;
- определение критериев проверки и closeout.

Именно здесь агентная организация начинает вести себя как виртуальная компания, а не как единичный чат-ассистент.

## Stage 7. Автономное исполнение

На этом этапе организация уже должна работать в основном сама.

Она:

- поднимает исполнительские роли;
- выполняет задачи;
- ведёт status board;
- делает проверки;
- делает integration;
- пишет evaluation and learning trace;
- эскалирует только действительно принципиальные вопросы.

## Stage 8. Closeout

После завершения волны организация должна:

- оставить прозрачный итог;
- показать, что сделано;
- показать, что не сделано;
- показать, где требовалось вмешательство человека;
- обновить knowledge и learning layer.

## Что обязательно должно быть скрыто от пользователя

Пользователь не должен быть обязан вручную:

- проектировать роли;
- писать AGENTS/CLAUDE-style governance файлы;
- строить task graph;
- придумывать state layer;
- вручную удерживать организационную память;
- координировать ветки вручную через чат.

Именно это и должен брать на себя plug-and-play слой.

## Что пользователь всё ещё должен делать

Пользователь по-прежнему остаётся:

- источником high-level intent;
- источником бизнес-критериев;
- арбитром спорных или необратимых решений;
- владельцем проекта.

То есть цель не в том, чтобы пользователь исчез.

Цель в том, чтобы он перестал быть ручным диспетчером каждого мелкого шага.

## Минимальный состав продукта для реального plug-and-play

Чтобы этот формат считался реально достигнутым, должны существовать:

1. install script или иной воспроизводимый способ развернуть scaffold;
2. starter project structure;
3. один нормализованный входной формат;
4. bootstrap path;
5. starter policies;
6. runtime baselines;
7. handoff protocol от пользователя к агентной организации;
8. execution and escalation model;
9. closeout and learning model.

## Признаки готовности с точки зрения пользователя

Формат можно считать готовым, если пользователь может:

1. создать папку;
2. запустить один install step;
3. описать своё намерение;
4. запустить handoff;
5. дальше наблюдать уже не хаотическую переписку, а организованный pipeline работы.

## Признаки того, что формат ещё не готов

Формат ещё не готов, если:

- пользователю приходится вручную собирать организационные файлы;
- пользователю приходится самому решать, какие роли создавать;
- пользователю приходится самому превращать свой запрос в инженерное ТЗ;
- агентная организация не может сама пройти путь от intake до execution plan;
- большая часть управления снова превращается в ручной чат.

## Практический вывод

Итоговая цель сформулирована правильно:

**пользователь не должен проектировать агентную организацию каждый раз заново. Он должен устанавливать её как дистрибутив, задавать намерение и передавать ей дальнейшую организацию работы.**

А значит следующий уровень зрелости уже не про новые методологические тексты, а про:

- качество starter kit;
- качество intake normalization;
- качество handoff;
- качество автономного execution pipeline после handoff.
