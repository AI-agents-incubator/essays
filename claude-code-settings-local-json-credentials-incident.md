# Инцидент безопасности: утечка кредов в `.claude/settings.local.json`

> Версия файла: `v1.0`
> Дата версии: `2026-03-20`
> Тип документа: `security incident note`

## Что произошло

В реальной работе был обнаружен опасный паттерн:
локальный файл `.claude/settings.local.json` оказался заполнен не только harmless-настройками, но и полными строками команд, внутри которых уже лежали чувствительные данные.

В таких строках могли оказаться:

- приватные SSH-ключи;
- JWT-токены;
- `SERVICE_ROLE_KEY`;
- IP-адреса, порты и имена пользователей;
- другие секреты, которые в нормальной архитектуре не должны жить в permission-файле.

## Как проблема была замечена

Не через аудит и не через встроенный security alert.

Проблема была замечена случайно: пользователь открыл `.claude/settings.local.json` в IDE и увидел, что внутри лежат не абстрактные permission patterns, а почти готовые рабочие команды с чувствительными аргументами.

Это важно:
если бы файл не был открыт вручную, такой риск мог бы оставаться невидимым очень долго.

## Почему это могло произойти

Причина не в "магической поломке", а в ожидаемом поведении системы разрешений.

Когда Claude Code предлагает выполнить команду, пользователь может нажать `Allow`.
После этого локальное разрешение сохраняется, чтобы не спрашивать заново.

Если команда была дана в виде полной строки, например:

```text
ssh -i ~/.ssh/claude_prod_new -p 65002 user@1.2.3.4 "команда"
```

то при неосторожной практике в локальный permission-layer может попасть именно эта строка целиком,
вместе с:

- путями к ключам;
- адресами;
- портами;
- пользователями;
- токенами в заголовках `curl`;
- другими чувствительными аргументами.

## Корень проблемы

Корневая причина — хаотическое управление разрешениями.

Плохой режим выглядит так:

- пользователь жмёт `Allow`, чтобы просто убрать лишнее трение;
- никто не проверяет, что именно сохраняется;
- креды передаются прямо в строке команды;
- permission-файл превращается в неконтролируемый склад секретов;
- защита файла от git держится только на локальных исключениях одной машины.

## Почему это опасно

Даже если утечки наружу фактически не произошло, это всё равно реальный security incident.

Если бы такой файл:

- случайно попал в git;
- был скопирован на другую машину;
- попал в backup, лог, архив или attachment;
- оказался в общем diff;

то в историю репозитория или в другой контур ушли бы уже не просто настройки, а реальные секреты.

## Правильная модель

Нужны три жёстких правила.

### 1. Разрешения отдельно, секреты отдельно

Permission-файл не должен хранить реальные значения.

В нём допустимы только:

- общие паттерны действий;
- общие правила доступа;
- режимы `allow / ask / deny`;
- локальные overrides без секретов.

А вот это не должно жить в permission-layer:

- приватные ключи;
- токены;
- пароли;
- строки подключения;
- inline `Authorization` headers;
- конкретные SSH-команды с чувствительными аргументами.

### 2. Нельзя нажимать `Allow` на команду с inline creds

Перед нажатием `Allow` нужно спросить себя:

"Есть ли в этой строке секреты, токены, IP, приватные ключи или другие чувствительные данные?"

Если да, сначала:

- вынести креды во внешний секретный слой;
- запускать команду через безопасный wrapper, env-file или другой механизм;
- и только потом разрешать уже secret-free форму команды.

### 3. `.claude/settings.local.json` должен быть защищён на уровне репозитория

Нельзя полагаться только на локальный `.git/info/exclude`.

Защита должна быть частью общей структуры проекта:

```gitignore
# Claude Code local permissions — NEVER commit
.claude/settings.local.json
```

Иначе безопасность зависит не от репозитория, а от удачи и от настроек одной машины.

## Практические инварианты

После этого инцидента полезно считать обязательными такие правила:

1. `.claude/settings.local.json` — это не harmless config, а потенциально secret-adjacent файл.
2. Этот файл нужно периодически просматривать, а не считать "внутренним мусором".
3. Inline credentials нельзя одобрять через `Allow`.
4. Permission patterns должны быть максимально общими и secret-free.
5. Все реальные секреты должны жить вне командной строки и вне permission-файлов.
6. Репозиторий должен явно защищать `.claude/settings.local.json` от коммита.
7. Preflight для автономной работы должен проверять, что local permission-layer не превратился в хранилище секретов.

## Вывод

Этот инцидент показывает простую, но важную вещь:

**безопасность ломается не только через "взлом", но и через неосознанную рутину.**

Один клик `Allow`, сделанный без проверки строки команды, может создать не абстрактный, а вполне реальный канал утечки.

Поэтому permission-system надо воспринимать не как удобный механизм "чтобы меньше спрашивало",
а как часть security architecture.
