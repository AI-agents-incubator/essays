# Runtime Status Protocol

> Версия файла: `v1.0`
> Дата версии: `2026-03-17`
> Тип документа: `signal protocol`

## Назначение

Этот протокол задаёт простой сигнальный слой для двух независимых runtime-песочниц:

- `Codex`
- `Claude Code`

Сигнализация строится не на фоне демона и не на внешнем мониторинге, а на явных status-артефактах внутри каждой sandbox.

## Базовый принцип

Каждый runtime обязан поддерживать свой файл состояния:

- `runtimes/codex/runs/RUNTIME_STATUS.md`
- `runtimes/claudecode/runs/RUNTIME_STATUS.md`

Именно этот файл считается главным сигналом для наблюдателя.

## Допустимые статусы

- `planned` — запуск ещё не начался
- `in_progress` — агент выполняет текущий run
- `blocked` — run остановлен из-за локальной проблемы, но без обязательной эскалации человеку
- `escalation_required` — run не может быть продолжен без решения человека
- `completed` — run успешно завершён и оставил все обязательные артефакты
- `failed` — run завершился неуспешно

## Обязательные поля

Каждый `RUNTIME_STATUS.md` должен содержать минимум:

- `runtime`
- `current_run`
- `status`
- `started_at`
- `updated_at`
- `summary_file`
- `evaluation_file`
- `needs_human`
- `next_run`
- `blocking_issue`

## Правила обновления

### В начале run

Агент обязан:

- выставить `status: in_progress`
- заполнить `started_at`, если запуск идёт впервые
- обновить `updated_at`
- указать активный `current_run`

### Во время run

Агент обязан обновлять `updated_at`, если:

- произошёл переход в другой статус
- появилась блокировка
- изменился путь к итоговым артефактам

### В конце run

Если run завершён успешно, агент обязан:

- выставить `status: completed`
- указать `summary_file`
- указать `evaluation_file`
- указать `next_run`
- выставить `needs_human: no`, если эскалация не нужна

Если run не может продолжаться без участия человека, агент обязан:

- выставить `status: escalation_required`
- выставить `needs_human: yes`
- кратко заполнить `blocking_issue`

## Что делает наблюдатель

Наблюдатель не должен угадывать состояние sandbox по косвенным признакам.

Он смотрит в три места:

1. `RUNTIME_STATUS.md`
2. указанный `summary_file`
3. указанный `evaluation_file`

Этого достаточно для первой версии сигнального слоя.

## Почему без демона

Для текущей стадии отдельный демон не нужен, потому что:

- архитектура ещё меняется;
- сначала важно формализовать сам протокол;
- файловый статус прозрачен, проверяем и легко расширяется;
- позже поверх него можно поднять polling, automation или dashboard.
